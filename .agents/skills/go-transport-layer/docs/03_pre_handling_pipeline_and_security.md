# خط أنابيب المعالجة المسبقة المكون من 6 مراحل والحدود الأمنية

توضح هذه الوثيقة دورة الحياة المتسلسلة التي يخضع لها كل طلب وارد قبل دخوله إلى معالج التطبيق، متضمنة التعافي من الانهيارات، وتتبع الارتباط الموزع، واستخراج الهوية الأمنية، والتحقق النحوي.

---

## 1. تسلسل دورة الحياة (Lifecycle Sequence)

```text
دخول الطلب عبر الشبكة (Request Ingress)
      │
      ▼
[المرحلة 1] وسم البروتوكول والتعافي الآمن من الانهيار (Panic Recovery)
      │
      ▼
[المرحلة 2] معرف الارتباط والتتبع الموزع (X-Request-ID و W3C traceparent)
      │
      ▼
[المرحلة 3] تطبيع البيانات الوصفية وحقن السياق (IP العميل، والترويسات)
      │
      ▼
[المرحلة 4] المصادقة واستخراج الهوية الأمنية SecurityPrincipal (JWT / API Key)
      │
      ▼
[المرحلة 5] فك التشفير والتحقق النحوي من الحمولة (Syntactic Validation)
      │
      ▼
[المرحلة 6] فرض المهل الزمنية للسياق والحدود القصوى لمعدل الطلبات
      │
      ▼
تسليم الطلب لحالة الاستخدام النقية للتطبيق (Execute)
```

---

## 2. تفصيل المراحل الست (Deep Dive)

### المرحلة 1: وسم البروتوكول والتعافي من الانهيار (Protocol Stamping & Panic Recovery)

1. **وسم البروتوكول (Protocol Stamping)**: يحدد محول النقل مسار الدخول (`ProtocolHTTP` مقابل `ProtocolGRPC`) ويسجله داخل `TransportInfo`.
2. **التعافي من الانهيار (Panic Recovery)**: تعتمد حدود النقل معترض تعافٍ مؤجل (`defer`).
   - في حال حدوث هلع (مثل إلغاء إشارة مؤشر فارغ nil pointer dereference أو تجاوز حدود المصفوفة)، يلتقط المعترض الهلع فوراً.
   - يتم تسجيل قيمة الهلع وتتبع المكدس (Stack Trace) في القياسات المنظمة (`slog.Error`).
   - يُعاد للعميل خطأ معياري آمن (`500 Internal Server Error` في HTTP، أو `codes.Internal` في gRPC) دون كشف تفاصيل المكدس للمتصل الخارجي.

### المرحلة 2: معرف الارتباط والتتبع الموزع (Correlation ID & Distributed Tracing)

تتطلب الأنظمة الموزعة معرف ارتباط يربط الطلبات عبر الخدمات المصغرة المتعددة:

1. **الاستخراج (Extraction)**:
   - HTTP: قراءة ترويسة `X-Request-ID` أو `X-Correlation-ID`.
   - gRPC: قراءة `x-request-id` من البيانات الوصفية الواردة `metadata.MD`.
2. **التوليد (Generation)**: في حال غيابه، يتم توليد معرف فريد عشوائي أو قابل للترتيب الزمني (`UUIDv7` أو سلسلة سداسية عشرية بطول 128 بت).
3. **التمرير (Propagation)**:
   - HTTP: كتابة `X-Request-ID` في ترويسات الاستجابة الصادرة `w.Header()`.
   - gRPC: استدعاء `grpc.SetHeader(ctx, metadata.Pairs("x-request-id", reqID))`.
4. **سياق تتبع W3C (W3C TraceContext)**: في حال وجود ترويسة `traceparent` (مثل `00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01`)، يتم استخراجها وربطها بنطاق OpenTelemetry.

### المرحلة 3: تطبيع البيانات الوصفية (Metadata Normalization)

يتعامل HTTP و gRPC مع البيانات الوصفية بآليات مختلفة:

- **HTTP**: ترويسات غير حساسة لحالة الأحرف يُصل إليها عبر `http.Header.Get()`، والتي تطبع المفاتيح اصطلاحياً (مثل `Authorization`).
- **gRPC**: تكون مفاتيح البيانات الوصفية دائماً بأحرف صغيرة داخل `metadata.MD` (مثل `authorization`).
- **التوحيد**: تقوم دالة `TransportContext.Header(key)` بتوحيد البحث بحيث لا تحتاج الفحوصات الأمنية إلى تفرعات شرطية خاصة بالبروتوكول.
- **عنوان IP للعميل**: فحص `X-Forwarded-For` (العنوان الأول)، و `X-Real-IP`، وعنوان النظير المباشر TCP عبر `net.SplitHostPort`.

### المرحلة 4: المصادقة وحل الهوية الأمنية (Authentication & SecurityPrincipal)

تتحقق المصادقة من *هوية* المتصل:

1. **استخراج بيانات الاعتماد**:
   - البحث عن ترويسة `Authorization: Bearer <token>`.
   - البحث عن مفاتيح API في `X-API-Key` أو البيانات الوصفية.
2. **التحقق التشفيري**:
   - التحقق من صحة التوقيع الرقمي (HMAC-SHA256 أو RSA أو Ed25519).
   - التحقق من صلاحية الوقت (`exp > now`) وبدء الصلاحية (`nbf <= now`).
3. **إنشاء كائن الهوية الأمنية (Principal Creation)**:
   - مطابقة الادعاءات مع كائن `SecurityPrincipal` نقي: `UserID`، `TenantID`، `Roles`، `Scopes`.
   - حقن الهوية في `TransportContext.SetPrincipal()` و `context.Context` عبر `WithPrincipal(ctx, principal)`.

### المرحلة 5: التحقق النحوي للحمولة مقابل التحقق الدلالي للنطاق

فصل حاسم ومبدئي للمسؤوليات الهندسية:

- **التحقق النحوي (حدود النقل Syntactic Validation)**:
  - هل هيكل JSON تالف أو غير صالح؟
  - هل الحقول الإلزامية موجودة في الطلب؟
  - هل النصوص والرموز ضمن القيود المحددة للأطوال؟
  - هل صيغة البريد الإلكتروني أو معرف UUID صحيحة؟
  - **الإجراء**: يتم داخل محول النقل / فك التشفير. في حال عدم الصلاحية، يُرفض الطلب فوراً برمز `400 Bad Request` أو `codes.InvalidArgument` قبل ملامسة خدمات النطاق.
- **التحقق الدلالي / الخاص بنطاق الأعمال (Application Core Semantic Validation)**:
  - هل يمتلك هذا الحساب رصيداً كافياً لإتمام العملية؟
  - هل حالة هذا الطلب مؤهلة للإلغاء في هذه اللحظة؟
  - **الإجراء**: يتم معالجته حصرياً داخل حالة الاستخدام (Use Case) أو كيان النطاق (Domain Entity).

### المرحلة 6: المهل الزمنية ومعدل استهلاك الطلبات (Deadlines & Rate Limiting)

1. **المهل الزمنية (Deadlines)**:
   - يقوم gRPC بتمرير المهل تلقائياً عبر ترويسة `grpc-timeout`، ويحولها محرك gRPC إلى `context.WithDeadline`.
   - يجب أن تفرض طلبات HTTP مهلة صريحة عبر `context.WithTimeout(ctx, defaultTimeout)` لمنع هجمات الإبطاء المتعمد (Slow-Loris) أو استنزاف موارد النظام.
2. **تحديد المعدل (Rate Limiting)**:
   - تطبيق خوارزميات دلو الرموز (Token Bucket) أو النوافذ المنزلقة استناداً إلى `ClientIP` (لنقاط النهاية العامة) أو `Principal.TenantID` / `Principal.UserID` (للمستخدمين الموثقين).
   - عند تجاوز الحد المسموح، تُعاد استجابة `429 Too Many Requests` أو `codes.ResourceExhausted`.

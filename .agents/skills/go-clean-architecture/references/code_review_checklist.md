# قائمة مراجعة المعمارية النظيفة (Clean Architecture Code Review Checklist)

تُستخدم هذه القائمة أثناء مراجعة الكود (Code Review) أو عند إضافة أي ميزة أو مسار جديد في المشروع لضمان الالتزام الصارم بالمعايير الهندسية.

---

## بنود التدقيق المعماري

### 1. طبقة النطاق (Domain Layer)

- [ ] هل ملفات `internal/domain` خالية تماماً من استيراد أي حزم خارجية؟
- [ ] هل كائنات النطاق (Entities) خالية من وسوم `json:` و `db:`؟
- [ ] هل يتم التحقق من صحة القواعد وثوابت النطاق (Invariants) داخل الكيانات نفسها؟
- [ ] هل تم تعريف أخطاء النطاق كـ Sentinel Errors صريحة (مثل `ErrNotFound`)؟

### 2. طبقة حالات الاستخدام (Use Case Layer)

- [ ] هل تعتمد الـ Use Cases حصرياً على واجهات (Interfaces / Ports) للتعامل مع التخزين والخدمات الخارجية؟
- [ ] هل تم تعريف الـ Interfaces في نفس حزمة الـ usecase المستهلكة لها؟
- [ ] هل المدخلات عبارة عن أوامر واستعلامات واضحة (`Command` / `Query`) وليست كائنات HTTP؟
- [ ] هل يمكن كتابة اختبارات وحدة للـ Use Case بنسبة 100% باستخدام Function Mocks بدون أي اتصال شبكي؟

### 3. طبقة المحولات (Adapters Layer)

- [ ] هل تقتصر مسؤولية متحكمات الـ HTTP (`internal/adapters/http`) على: تفكيك الـ JSON، التحقق من التنسيق، استدعاء الـ Usecase، وإعادة الاستجابة؟
- [ ] هل تخلو متحكمات الـ HTTP من أي منطق أعمال أو استعلامات SQL مباشرة؟
- [ ] هل محولات التخزين (`internal/adapters/storage`) هي المكان الوحيد الذي يحتوي على كود SQL و `pgx`؟
- [ ] هل تقوم الـ Repositories بتحويل صفوف قاعدة البيانات إلى كيانات النطاق (`domain.Entity`) بشكل سليم؟

### 4. طبقة المنصة والتجميع (Platform Layer)

- [ ] هل يتم تجميع وربط كافة التبعيات حصرياً داخل جذر التكوين (`internal/platform/app`)؟
- [ ] هل تم تجنب استخدام أطر عمل الـ Reflection المعقدة لصالح الـ Explicit Constructor Injection؟
- [ ] هل يخلو دليل `internal/platform` من أي منطق أعمال مؤسسي؟

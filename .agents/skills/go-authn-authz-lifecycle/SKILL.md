# مهارة دورة حياة المصادقة (AuthN) والتفويض (AuthZ) في Go

تحدد هذه المهارة المعايير الهندسية والإنتاجية الشاملة والمحايدة تماماً لأطر العمل (Framework-Agnostic) لإدارة **دورات حياة المصادقة (Authentication - AuthN) والتفويض (Authorization - AuthZ)** في خدمات وأنظمة **Go**. تضع المهارة خطوط دفاع وفصل معماري صارمة عند **طبقة النقل (Transport/API Layer)** لحركة المرور الشبكية (HTTP/REST, gRPC, WebSocket)، وتوفر واجهات موحدة محايدة للبروتوكول، وتمنع أخطر الثغرات الأمنية مثل تجاوز الصلاحيات على مستوى الكائن (BOLA/IDOR)، وهجمات خلط الخوارزميات (Algorithm Confusion)، وتسرب تفاصيل البروتوكول إلى طبقة منطق الأعمال (Domain Leakage).

تستند هذه المعمارية إلى:

- **معايير IETF الدولية**: RFC 6749 و RFC 6750 (إطار OAuth 2.0 ورموز Bearer)، RFC 7519 (رموز JWT)، RFC 9068 (ملف JWT المعياري لرموز الوصول)، RFC 7662 (استبطان الرموز Token Introspection)، و RFC 7807 (تفاصيل المشاكل البرمجية Problem Details).
- **معايير NIST الأمنية**: معيار NIST SP 800-162 للتحكم المبني على السمات (ABAC)، معيار NIST SP 800-207 للأمان القائم على الثقة المعدومة (Zero Trust Architecture)، ومعمارية XACML / NIST الفيدرالية (PEP, PDP, PIP, PAP).
- **أفضل ممارسات Go الرسمية**: التوجيه الرسمي لنقل الهوية بأمان عبر `context.Context` باستخدام أنواع مفاتيح غير مصدّرة ([pkg.go.dev/context](https://pkg.go.dev/context))، وخطوط وسائط `net/http`، ومعترضات `grpc.UnaryServerInterceptor`.
- **محركات السياسات الرائدة**: محرك Open Policy Agent (OPA)، محرك Casbin بنموذج PERM، ومعمارية علاقات التفويض ReBAC المبنية على ورقة Google Zanzibar (SpiceDB / OpenFGA).

## المبادئ الأمنية والهندسية الحاكمة (Production Principles)

1. **الفصل المعماري الصارم بين AuthN والتفويض الخشن والتفويض الدقيق**:
   - **المصادقة (AuthN)**: تجيب عن: *"مَن أنت؟"* عبر فحص وتدقيق البراهين الرياضية وتجسيد كائن الهوية المطهر `*Principal` وحقنه في السياق.
   - **التفويض الخشن (Coarse AuthZ)**: يجيب عن: *"هل يمتلك دورك أو نطاق الرمز (Scope) تصريحاً باستدعاء هذا المسار/التابع؟"*، ويُنفّذ فورياً عند حافة النقل (Transport PEP) لضمان الفشل السريع (Fast-Fail).
   - **التفويض الدقيق (Fine AuthZ)**: يجيب عن: *"هل يحق لهذا المستخدم تنفيذ هذا الإجراء على هذا الكيان المالي/التجاري المحدد بناءً على سماته وحالته وعزل المستأجر؟"*، ويُنفّذ حصراً داخل طبقة التطبيق والـ Domain بالاستعانة بمستودعات البيانات (PIP) ومحرك السياسات (PDP).

2. **منع تسرب تفاصيل البروتوكول الشبكي (Zero Protocol Leakage)**:
   يُحظر تماماً تمرير كائنات `*http.Request` أو ترويسات HTTP أو ملفات تعريف الارتباط أو بيانات `metadata.MD` لـ gRPC أو سلاسل الرموز الخام إلى طبقة التطبيق أو الـ Domain. الكيان الوحيد المسموح بتمريره هو كائن الهوية المطهر `*Principal` عبر `context.Context`.

3. **حماية السياق بنوع مفتاح غير مصدّر (Type-Safe Context Keying)**:
   يجب حقن واسترجاع الهوية من `context.Context` عبر نوع بنية فارغة خاصة غير مصدّرة (`type contextKey struct{}`) لمنع أي تصادم أو تعديل من حزم خارجية.

4. **الصرامة التشفيرية والتحصين ضد هجمات خلط الخوارزميات (Alg Confusion Defense)**:
   يجب التحقق البرمجي الإلزامي من مطابقة خوارزمية التوقيع في ترويسة الرمز (`token.Header["alg"]`) للنوع المتوقع المعتمد (مثل `*jwt.SigningMethodRSA`). يجب رفض خوارزمية `none` ومحاولات توقيع HMAC باستخدام المفاتيح العامة فوراً.

5. **الفصل الدلالي الصارم بين رمزي الخطأ 401 و 403**:
   - يُرجع الخادم **`401 Unauthorized`** (`codes.Unauthenticated`) فقط وفقط إذا فشلت المصادقة (التوكن مفقود، منتهي الصلاحية، توقيعه مشوه).
   - يُرجع الخادم **`403 Forbidden`** (`codes.PermissionDenied`) عندما تكون الهوية مثبتة وصحيحة ولكنها تفتقر للصلاحية المطلوبة.
   - يُمنع منعاً باتاً إرجاع 401 عند عجز الصلاحيات حتى لا تقوم تطبيقات العميل بتسجيل خروج المستخدم دون مبرر.

6. **عزل المستأجرين المتعددين في أدنى طبقة (Multi-Tenancy at Persistence Layer)**:
   لا يُكتفى بحماية النقل لعزل المنظمات والشركات. يجب أن يُحقن `tenant_id` المستخرج حصرياً من الـ `Principal` الموثق كشرط إلزامي في كافة استعلامات قاعدة البيانات (`WHERE tenant_id = $1`) أو تطبيقه عبر Row-Level Security (RLS) في PostgreSQL لمنع ثغرات BOLA/IDOR.

7. **سجلات التدقيق الأمني ومغلفات الأخطاء المعيارية (RFC 7807)**:
   كل رفض لتفويض يجب أن يُسجل في سجلات التدقيق الأمني (`slog.WarnContext`) متضمناً معرّف الفاعل، معرّف المستأجر، الإجراء المطلوب، معرّف المورد، والـ IP، مع إرجاع استجابة RFC 7807 دون تسريب أي بيانات للبنية التحتية.

## الواجهات البرمجية الموحدة والمحايدة للبروتوكول (Unified Interfaces)

```go
package security

import (
 "context"
 "errors"
 "time"
)

// الأخطاء القياسية المعيارية
var (
 ErrUnauthenticated  = errors.New("security: unauthenticated, invalid or missing credentials")
 ErrTokenExpired     = errors.New("security: token has expired")
 ErrPermissionDenied = errors.New("security: permission denied, insufficient privileges")
)

// HeaderCarrier واجهة تجريدية لقراءة الترويسات بغض النظر عن البروتوكول (HTTP أو gRPC Metadata)
type HeaderCarrier interface {
 Get(key string) string
}

// Principal يمثل كائن الهوية النهائي الموثق والمطهر وغير القابل للتعديل
type Principal struct {
 ID         string
 TenantID   string
 Email      string
 Roles      map[string]struct{}
 Scopes     map[string]struct{}
 Attributes map[string]any
 IssuedAt   time.Time
 ExpiresAt  time.Time
}

func (p *Principal) HasRole(role string) bool {
 if p == nil {
  return false
 }
 _, ok := p.Roles[role]
 return ok
}

func (p *Principal) HasScope(scope string) bool {
 if p == nil {
  return false
 }
 _, ok := p.Scopes[scope]
 return ok
}

// Authenticator واجهة استخراج الهوية وفحص البراهين
type Authenticator interface {
 Authenticate(ctx context.Context, carrier HeaderCarrier) (*Principal, error)
}

// TokenValidator واجهة فحص وتدقيق الرموز الرقمية (JWT, PASETO)
type TokenValidator interface {
 ValidateToken(ctx context.Context, rawToken string) (*Principal, error)
}

// Action نوع العملية المطلوب تنفيذها
type Action string

const (
 ActionCreate  Action = "create"
 ActionRead    Action = "read"
 ActionUpdate  Action = "update"
 ActionDelete  Action = "delete"
 ActionApprove Action = "approve"
)

// Resource يمثل المورد التجاري الخاضع للتقييم والتفويض
type Resource struct {
 Type       string
 ID         string
 TenantID   string
 Attributes map[string]any
}

// Authorizer واجهة محرك تقييم السياسات واتخاذ القرار (PDP)
type Authorizer interface {
 Authorize(ctx context.Context, sub *Principal, act Action, res Resource) (bool, error)
}
```

## إدارة السياق بأمان تام (Safe Context Propagation)

```go
package security

import "context"

// نوع بنية فارغة غير مصدّر يمنع تصادم المفاتيح الرياضي
type contextKey struct{}

var principalKey = contextKey{}

// InjectPrincipal يحقن كائن الهوية الموثق داخل السياق
func InjectPrincipal(ctx context.Context, p *Principal) context.Context {
 return context.WithValue(ctx, principalKey, p)
}

// ExtractPrincipal يسترجع الهوية من السياق مع التحقق من النوع
func ExtractPrincipal(ctx context.Context) (*Principal, bool) {
 p, ok := ctx.Value(principalKey).(*Principal)
 return p, ok && p != nil
}

// MustExtractPrincipal يسترجع الهوية أو يعيد خطأ عدم المصادقة للمسارات المحمية
func MustExtractPrincipal(ctx context.Context) (*Principal, error) {
 p, ok := ExtractPrincipal(ctx)
 if !ok {
  return nil, ErrUnauthenticated
 }
 return p, nil
}
```

## دورتا الحياة السداسيتان (The Dual 6-Phase Lifecycles)

### أولاً: دورة حياة المصادقة (AuthN Lifecycle - 6 خطوات)

```text
┌─────────────────────────┐
│ 1. الاستخراج            │ استخراج ترويسة Bearer أو الكوكي أو gRPC metadata أو شهادة العميل mTLS
└───────────┬─────────────┘
            ▼
┌─────────────────────────┐
│ 2. الفحص الشكلي والتنقية │ التحقق من النمط (Bearer <token>) وتجاوز الرموز المشوهة دون استهلاك التشفير
└───────────┬─────────────┘
            ▼
┌─────────────────────────┐
│ 3. التحقق التشفيري       │ التحقق الرياضي من التوقيع عبر المفتاح العام ومكافحة هجمات خلط الخوارزميات
└───────────┬─────────────┘
            ▼
┌─────────────────────────┐
│ 4. تدقيق الادعاءات      │ فحص تاريخ الانتهاء (مع هامش Leeway)، والجمهور aud، والمصدر iss، والإلغاء
└───────────┬─────────────┘
            ▼
┌─────────────────────────┐
│ 5. تجسيد كائن الهوية     │ تحويل الادعاءات إلى كائن Go محكم الأنواع (*Principal) بخرائط O(1)
└───────────┬─────────────┘
            ▼
┌─────────────────────────┐
│ 6. حقن السياق والتسليم   │ حقن *Principal داخل context.Context وتسليم الطلب للمرحلة التالية
└─────────────────────────┘
```

### ثانياً: دورة حياة التفويض (AuthZ Lifecycle - 6 خطوات)

```text
┌─────────────────────────┐
│ 1. استرجاع الهوية       │ استخراج *Principal من السياق، ورفض الطلب فوراً بـ 401 إن لم توجد
└───────────┬─────────────┘
            ▼
┌─────────────────────────┐
│ 2. مطابقة الهدف والعملية │ مطابقة مسار وطريقة HTTP أو RPC مع العملية (Action) ونوع المورد (Resource)
└───────────┬─────────────┘
            ▼
┌─────────────────────────┐
│ 3. التفويض الخشن بالنقل │ التحقق من نطاقات OAuth والأدوار العامة عند حافة النقل (رفض سريع بـ 403)
└───────────┬─────────────┘
            ▼
┌─────────────────────────┐
│ 4. إثراء بيانات الكيان   │ في Use Case: جلب المورد من قاعدة البيانات (PIP) مقيداً بهوية المستأجر
└───────────┬─────────────┘
            ▼
┌─────────────────────────┐
│ 5. قرار التفويض الدقيق  │ تقييم سياسة PDP: Decision = Evaluate(Subject, Action, Resource, Environment)
└───────────┬─────────────┘
            ▼
┌─────────────────────────┐
│ 6. الفرض والتدقيق       │ السماح: تنفيذ منطق الأعمال | المنع: تدوين سجل أمني + إرجاع RFC 7807 (403)
└─────────────────────────┘
```

## الهياكل المعمارية ثلاثية الأبعاد (Architectural Topologies)

تعمل أنظمة الأمان المتطورة في Go عبر **ثلاثة أبعاد هندسية متزامنة**:

1. **البعد الخطي (Linear Pipeline - وسائط النقل)**:
   - تتابع تسلسلي صارم: Rate Limiter $\rightarrow$ AuthN PEP $\rightarrow$ Coarse AuthZ $\rightarrow$ Router.
   - يوفر آلية القطع السريع (Short-Circuit) لتوفير موارد الخادم.

2. **البعد المتداخل (Nested / Onion Layers - الدفاع في العمق)**:
   - **الحلقة الأولى (Perimeter)**: عزل الشبكة ومصادقة mTLS عند البوابة.
   - **الحلقة الثانية (Transport Ingress)**: فحص صحة التوكن والنطاقات العامة.
   - **الحلقة الثالثة (Domain Core)**: فحص قيود وقواعد الأعمال وحالة الكيان.
   - **الحلقة الرابعة (Data Layer)**: تصفية الاستعلامات إجبارياً بحسب المستأجر (`WHERE tenant_id = $1`) وسياسات PostgreSQL RLS.

3. **البعد الشبكي (Mesh & Graph Relationships - ReBAC & Zero Trust)**:
   - **شبكة الخدمات (Service Mesh)**: الاتصال الداخلي بين الخدمات المصغرة محمي بهويات SPIFFE/SPIRE المشفرة.
   - **علاقات الموارد (ReBAC)**: استنتاج الصلاحيات عبر اجتياز العقد في الرسم البياني للعلاقات (نموذج Google Zanzibar / SpiceDB).

## مصفوفات المفاضلة والقرارات المعمارية (Decision Matrices)

### جدول 1: مقارنة تقنيات المصادقة (AuthN Mechanisms)

| المعيار | رموز JWT عديمة الحالة | الرموز المبهمة (Opaque) | شهادات mTLS X.509 | توقيع HMAC الطلبي |
| :--- | :--- | :--- | :--- | :--- |
| **مكان التخزين** | في الرمز نفسه (Client) | قاعدة بيانات أو Redis (Server) | ملفات الشهادات / HSM | مفتاح سري مشترك |
| **زمن التحقق (Latency)** | فائق الصغر ($\approx 0.1\text{ms}$) | يحتاج لطلب شبكي ($5\text{--}20\text{ms}$) | شبه معدوم بعد المصافحة | فائق الصغر ($\approx 0.05\text{ms}$) |
| **إمكانية الإلغاء الفوري** | صعبة وتتطلب قوائم حظر | فورية ومباشرة بحذف المفتاح | عبر قوائم CRL / OCSP | فورية بإلغاء أو تدوير المفتاح |
| **استهلاك الترويسة** | متوسط إلى كبير (0.5KB -- 2KB) | صغير جداً (32 -- 64 بايت) | لا تستهلك ترويسات التطبيق | صغير (توقيع وبصمة) |
| **الأنسب لـ** | واجهات الويب وتطبيقات الموبايل | الأنظمة البنكية والمالية الحرجة | التواصل الداخلي بين الـ Microservices | التكامل المبرمج بين الأنظمة B2B |

### جدول 2: مقارنة محركات ونماذج التفويض (AuthZ Engines)

| المعيار | الشروط المكتوبة برمجياً (Native Go) | محرك Casbin (`casbin/v2`) | محرك OPA (Open Policy Agent) | محرك Google Zanzibar (SpiceDB) |
| :--- | :--- | :--- | :--- | :--- |
| **النموذج المدعوم** | منطق يدوي مخصص | PERM (RBAC, ABAC, ACL) | PBAC (لغة Rego التصريحية) | ReBAC (رسم بياني للعلاقات) |
| **نمط النشر** | مدمج داخل كود المصدر | مكتبة Go مدمجة في المعالج | خادم مستقل أو Sidecar أو WASM | خادم مستقل وقاعدة بيانات موزعة |
| **مرونة تحديث السياسة** | تتطلب إعادة بناء وتوزيع الكود | ديناميكية عبر قاعدة البيانات | ديناميكية عبر حزم السياسات | فورية بتحديث سجلات العلاقات |
| **زمن تقييم الصلاحية** | نانو ثانية (أسرع أداء) | ميكروثانية ($\approx 1\text{--}5\mu\text{s}$) | ميكرو إلى ملي ثانية | ملي ثانية ($3\text{--}15\text{ms}$) |
| **التعامل مع ملايين العلاقات** | مستحيل يدوياً | محدود بذاكرة الخدمة | يتطلب تحميل الرسوم البيانية | الأفضل عالمياً (Trillions of Tuples) |
| **الأنسب لـ** | تطبيقات بسيطة بأدوار ثابتة | تطبيقات أحادية أو متوسطة | بيئات Kubernetes والحوسبة السحابية | تطبيقات المشاركة والتعاون والمستأجرين |

## الأنماط المضادة الشائعة (Anti-Patterns to Avoid)

| النمط المضاد | سبب الفشل في الإنتاج | الحل الهندسي المعتمد |
| :--- | :--- | :--- |
| **الخلط بين AuthN و AuthZ** | تشابك فك تشفير التوكن مع فحص ملكية الكيانات يمنع إعادة استخدام الكود عبر البروتوكولات المختلفة. | فصل المصادقة لوسيط نقل مستقل، وتقسيم التفويض إلى خشن عند النقل ودقيق داخل التطبيق. |
| **تسرب البروتوكول إلى الـ Domain** | تمرير `*http.Request` أو سلاسل التوكن للـ Use Case يكسر المعمارية النظيفة ويعطل اختبارات الوحدة. | تجسيد وتطهير كائن الهوية `*Principal` وتمريره حصراً عبر `context.Context`. |
| **خلط الخوارزميات (`alg: none`)** | تمكين المهاجمين من تزوير رموز مقبولة بتوقيعات منزوعة أو استخدام المفتاح العام كسر HMAC. | التحقق الصارم من نوع الخوارزمية عبر `token.Method.(*jwt.SigningMethodRSA)`. |
| **إرجاع 401 عند عجز الصلاحية** | التسبب في جعل المتصفحات وتطبيقات الموبايل تسجل خروج المستخدم وتحوله لصفحة الدخول بلا مبرر. | إرجاع `401` للمصادقة فقط، وإرجاع `403 Forbidden` عندما تكون الهوية مثبتة لكن تفتقر للصلاحية. |
| **استقبال `tenant_id` من العميل** | يفتح ثغرة BOLA/IDOR الكارثية ويتيح للمخترق تعديل معاملات الرابط لاختراق بيانات الشركات المنافسة. | استخراج `tenant_id` حصرياً من ادعاءات التوكن الموثق داخل كائن `Principal`. |

## قائمة التحقق والاعتماد الأمني (Verification Checklist)

```text
[ ] وسيط المصادقة يتحقق من توقيع RSA/ECDSA مع التحقق من الصلاحية الزمنية، والمصدر، والجمهور، وهامش التوقيت
[ ] التحصين التام ضد هجوم خلط الخوارزميات عبر التحقق المباشر من نوع token.Method
[ ] تجسيد بيانات الهوية في كائن Go غير قابل للتعديل (*security.Principal) محتوياً على خرائط فحص سريعة
[ ] حقن واسترجاع الهوية من السياق يتم عبر نوع بنية خاصة غير مصدّرة (type contextKey struct{})
[ ] منع تسرب البروتوكول: لا يتم تمرير أي كائنات لـ HTTP أو gRPC أو توكنات خام لحالات الاستخدام
[ ] التفويض الخشن (OAuth Scopes والأدوار العامة) يُفرض عند حافة النقل مع إرجاع 403 Forbidden
[ ] التفويض الدقيق يُفحص داخل حالة الاستخدام بالاعتماد على إثراء بيانات المورد من المستودع (PIP)
[ ] عزل المستأجرين مفروض إجبارياً على مستوى قاعدة البيانات (WHERE tenant_id = $1 أو PostgreSQL RLS)
[ ] كل رفض أمني يُسجل في سجلات التدقيق الأمني ويُرجع استجابة مشكلة معيارية وفق RFC 7807
[ ] كلمات المرور والمفاتيح السرية والرموز الخام محجوبة كلياً من سجلات الخادم (Redacted)
```

# دورتا الحياة السداسيتان للمصادقة والتفويض (Six-Phase AuthN & AuthZ Lifecycles)

توضح هذه الوثيقة التفصيل التشغيلي والهندسي الكامل للدورتين المتتاليتين للأمان في خدمات Go: **دورة حياة المصادقة (AuthN Lifecycle)** تعقبها **دورة حياة التفويض (AuthZ Lifecycle)**.

---

## 1. دورة حياة المصادقة (AuthN Lifecycle - 6 مراحل)

```text
┌────────────────────────────────────────────────────────┐
│ 1. مرحلة الاستخراج (Extraction)                        │
│    الترويسات، ملفات Cookies، بيانات gRPC، شهادات mTLS   │
└──────────────────────────┬─────────────────────────────┘
                           │
                           ▼
┌────────────────────────────────────────────────────────┐
│ 2. التنقية والفحص الشكلي (Sanitization & Validation)   │
│    التحقق من بادئة Bearer وبنية أجزاء JWT الثلاثة      │
└──────────────────────────┬─────────────────────────────┘
                           │
                           ▼
┌────────────────────────────────────────────────────────┐
│ 3. التحقق التشفيري ومكافحة التلاعب (Crypto Check)      │
│    جلب مفاتيح JWKS، فحص خوارزمية التوقيع الرياضي       │
└──────────────────────────┬─────────────────────────────┘
                           │
                           ▼
┌────────────────────────────────────────────────────────┐
│ 4. تدقيق الادعاءات الزمنية (Claims & Temporal)         │
│    exp (مع هامش Leeway)، و nbf، و iat، و iss، و aud    │
└──────────────────────────┬─────────────────────────────┘
                           │
                           ▼
┌────────────────────────────────────────────────────────┐
│ 5. تجسيد كائن الهوية (Principal Materialization)       │
│    تحويل ادعاءات JSON إلى كائن Go محكم الأنواع          │
└──────────────────────────┬─────────────────────────────┘
                           │
                           ▼
┌────────────────────────────────────────────────────────┐
│ 6. حقن السياق والتسليم (Context Injection)             │
│    حقن كائن *Principal في السياق بنوع مفتاح خاص        │
└────────────────────────────────────────────────────────┘
```

### المرحلة 1: الاستخراج (Extraction)
يتم فحص واستخراج بيانات الاعتماد من ناقل الحركة:
- **في HTTP**: ترويسة `Authorization: Bearer <token>` أو ملف تعريف ارتباط موقع ومشفر.
- **في gRPC**: استخراج بيانات `metadata.MD` الوصفية بمفتاح `authorization`.
- **في mTLS**: استخراج شهادة العميل من `tls.ConnectionState.PeerCertificates[0]` عند طبقة النقل.

### المرحلة 2: التنقية والفحص الشكلي (Sanitization)
التأكد من أن الرمز يطابق البنية القياسية المكونة من ثلاثة أجزاء مفصولة بنقاط (`header.payload.signature`). يتم رفض المحارف غير المقبولة والأحجام المتضخمة فوراً دون استهلاك عمليات تشفير الحسابات الرياضية المكلفة.

### المرحلة 3: التحقق التشفيري ومكافحة هجمات الخلط (Crypto Verification)
1. **فحص الخوارزمية (Alg Check)**: التحقق الإلزامي من أن نوع الخوارزمية في الترويسة يطابق المتوقع:
   ```go
   if _, ok := token.Method.(*jwt.SigningMethodRSA); !ok {
       return nil, fmt.Errorf("unexpected signing method: %v", token.Header["alg"])
   }
   ```
2. **جلب المفاتيح العامة (JWKS)**: مطابقة معرف المفتاح `kid` مع المفاتيح المخبأة محلياً من خادم الهوية عبر بروتوكول JWKS.
3. **التدقيق الرياضي**: التحقق من صحة التوقيع الرقمي لمنع أي تلاعب بمحتوى الحمولة.

### المرحلة 4: تدقيق الادعاءات والصلاحية الزمنية (Claims Validation)
1. **هامش التوقيت الزمني (Clock Skew Leeway)**: إضافة هامش أمان زمني (30 إلى 60 ثانية) لتفادي فروق التوقيت البسيطة بين الخوادم الموزعة:
   ```go
   jwt.WithLeeway(30 * time.Second)
   ```
2. **فحص الادعاءات القياسية**:
   - `exp`: الرفض فوراً إذا انتهت صلاحية الرمز مع هامش السماح.
   - `nbf` و `iat`: الرفض إذا كان تاريخ السريان مستقبلياً.
   - `iss`: التأكد من مطابقة مصدر الرمز لنطاق خادم المصادقة المعتمد.
   - `aud`: التأكد من أن الرمز صادر خصيصاً لهذه الخدمة تحديداً لمنع هجمات تمرير الرموز (Token Forwarding).
3. **فحص الإلغاء (Revocation)**: فحص قائمة الرموز الملغاة أو مقارنة إصدار جلسة المستخدم المخزن في ذاكرة Redis.

### المرحلة 5: تجسيد كائن الهوية (Principal Materialization)
تحويل ادعاءات JSON الخام إلى كائن Go نقي ومحكم:
- تحويل مصفوفات النصوص (`roles`, `scopes`) إلى خرائط `map[string]struct{}` لضمان فحص العضوية الفوري في زمن $O(1)$.
- استخراج معرف المستخدم (`ID`) ومعرف المنظمة (`TenantID`).

### المرحلة 6: حقن السياق والتسليم (Context Injection)
حقن كائن الـ `*Principal` في سياق الطلب `context.Context` عبر الدالة المغلفة الآمنة، وتمرير الطلب للمعالج التالي.

## 2. دورة حياة التفويض (AuthZ Lifecycle - 6 مراحل)

```text
┌────────────────────────────────────────────────────────┐
│ 1. استرجاع الهوية من السياق (Principal Retrieval)       │
│    MustExtractPrincipal(ctx) -> 401 إن لم تكن موجودة   │
└──────────────────────────┬─────────────────────────────┘
                           │
                           ▼
┌────────────────────────────────────────────────────────┐
│ 2. مطابقة الهدف والعملية (Target & Action Mapping)     │
│    طريقة الطلب (GET->read)، ونوع المورد المستهدف       │
└──────────────────────────┬─────────────────────────────┘
                           │
                           ▼
┌────────────────────────────────────────────────────────┐
│ 3. التقييم الخشن عند النقل (Transport Coarse AuthZ)    │
│    فحص النطاقات (Scopes) والأدوار -> 403 إن كانت ناقصة │
└──────────────────────────┬─────────────────────────────┘
                           │
                           ▼
┌────────────────────────────────────────────────────────┐
│ 4. إثراء بيانات الكيان (Dynamic PIP Enrichment)        │
│    جلب الكيان من قاعدة البيانات مقيداً بـ TenantID      │
└──────────────────────────┬─────────────────────────────┘
                           │
                           ▼
┌────────────────────────────────────────────────────────┐
│ 5. تقييم السياسة الدقيقة (Fine-Grained PDP Decision)   │
│    Evaluate(Subject, Action, Resource, Environment)    │
└──────────────────────────┬─────────────────────────────┘
                           │
                           ▼
┌────────────────────────────────────────────────────────┐
│ 6. فرض القرار وسجل التدقيق (Enforcement & Audit Log)   │
│    السماح: استكمال العمل | المنع: تدقيق أمني + RFC 7807│
└────────────────────────────────────────────────────────┘
```

### المرحلة 1: استرجاع الهوية (Principal Retrieval)
يقوم وسيط التفويض أو حالة الاستخدام باستخراج `*Principal` من `context.Context`. إذا لم يكن موجوداً، يُلغى الطلب فوراً بخطأ `401 Unauthorized`.

### المرحلة 2: مطابقة الهدف والعملية (Target Mapping)
تحويل طلب النقل إلى كينونة عملية ومورد في المجال:
- مسار HTTP `GET /api/v1/invoices` $\rightarrow$ العملية: `read`، المورد: `invoice`.
- مسار HTTP `POST /api/v1/invoices/:id/approve` $\rightarrow$ العملية: `approve`، المورد: `invoice`.
- استدعاء gRPC `/billing.v1.Billing/ApproveInvoice` $\rightarrow$ العملية: `approve`، المورد: `invoice`.

### المرحلة 3: التقييم الخشن عند النقل (Transport Coarse PEP)
تقييم الصلاحيات العامة السريعة دون استدعاء أي مستودعات أعمال:
- هل يحمل الرمز نطاق OAuth المطلوب (`invoices:write`)؟
- هل يحمل الفاعل دوراً عاماً ضرورياً للمسار (`finance_manager`)؟
- في حال الإخفاق، يُقطع مسار الطلب فوراً برمز `403 Forbidden` (`codes.PermissionDenied`).

### المرحلة 4: إثراء بيانات الكيان والمجال (PIP Enrichment)
داخل حالة استخدام التطبيق، تستدعي نقطة جمع المعلومات (PIP) قاعدة البيانات:
- استرجاع المورد مقيداً بمعرف المستأجر `principal.TenantID`.
- إذا لم يُعثر على المورد، يُرجع خطأ `404 Not Found` لمنع تسريب وجود المورد.
- تعبئة سمات المورد في كائن `security.Resource` (مثل `owner_id`, `status`, `amount`).

### المرحلة 5: تقييم السياسة الدقيقة (Fine-Grained PDP)
تستدعي حالة الاستخدام محرك السياسات:
`allowed, err := authorizer.Authorize(ctx, principal, action, resource)`
يُقيم محرك القرارات القواعد المعقدة:
- هل الفاتورة في حالة مسودة `draft`؟
- هل يتجاوز المبلغ الحد المسموح للمدير؟
- هل يتبع المستخدم نفس الفرع والقسم؟

### المرحلة 6: فرض القرار وتدوين سجل التدقيق (Enforcement & Audit Logging)
1. **في حال السماح (Allow)**: تستكمل حالة الاستخدام تنفيذ منطق الأعمال وتعديل الحالة.
2. **في حال المنع (Deny)**:
   - تسجيل حدث أمني عالي الأهمية في سجلات التدقيق الأمني (`slog.WarnContext`) يتضمن: هوية المستخدم، هوية المستأجر، معرّف المورد، نوع العملية، وعنوان الـ IP.
   - إرجاع خطأ `ErrPermissionDenied`.
   - تقوم طبقة النقل بتغليف الاستجابة وفق معيار RFC 7807:
     ```json
     {
       "type": "https://httpstatuses.com/403",
       "title": "Forbidden",
       "status": 403,
       "detail": "Missing required permissions to approve this invoice",
       "instance": "/api/v1/invoices/inv_101/approve"
     }
     ```

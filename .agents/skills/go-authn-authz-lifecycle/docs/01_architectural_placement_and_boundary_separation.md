# التوزيع المعماري وفصل الحدود: طبقة النقل مقابل طبقة المجال (Transport vs Domain)

في الأنظمة الموزعة والتطبيقات السحابية المكتوبة بلغة **Go**، تعتمد المتانة الأمنية للمنظومة بالكامل على **أين** تُنفّذ الفحوصات الأمنية و**ما هي** المعلومات المصرح لكل طبقة بالاطلاع عليها. تفصل هذه الوثيقة الحدود السداسية الصارمة بين **طبقة النقل (Transport Layer - HTTP/gRPC)** و**نواة المجال والتطبيق (Application & Domain Core)**.

---

## 1. الإشكالية المعمارية الجوهرية: الخلط مقابل التسرب

### إشكالية الخلط (AuthN + AuthZ Conflation)

عندما يقوم المطورون بحشر منطق المصادقة والتفويض داخل وسيط برمجي واحد (Middleware) تظهر مشكلتان معماريتان خطيرتان:

1. **الارتباط المبكر بالمجال (Premature Domain Binding)**: يحاول الوسيط قراءة حمولة الطلب (Body) أو الاستعلام عن قاعدة البيانات قبل أن يقوم موجه المسارات (Router) بتحديد صحة المسار أصلاً.
2. **عجز إعادة الاستخدام (Inflexible Reuse)**: عند إضافة منافذ جديدة مثل gRPC أو WebSocket أو أوامر CLI، ينهار النظام ويتطلب إعادة كتابة منطق الأمان بالكامل لأنه مقيد بـ `net/http`.

### إشكالية تسرب البروتوكول إلى المجال (Domain Leakage)

المشكلة العكسية هي تفويض كافة الفحوصات الأمنية إلى طبقة التطبيق والـ Domain:

- تضطر طبقة المجال إلى استيراد حزم النقل (`net/http` أو `metadata.MD`).
- الطلبات الفاسدة أو غير المصادق عليها تخترق مكدس النظام وتستهلك موارد الذاكرة والاتصالات بقاعدة البيانات قبل اكتشاف رفضها.
- تصبح اختبارات الوحدة (Unit Tests) لحالات الاستخدام شديدة التعقيد لأنها تتطلب محاكاة طلبات HTTP كاملة وترويسات وهمية.

## 2. مصفوفة المسؤوليات والحدود المعمارية (Hexagonal Boundary Matrix)

| المسؤولية | طبقة النقل (Transport PEP Ingress) | الحدود و DTOs | طبقة التطبيق والمجال (Domain PEP) | طبقة البيانات والمستودعات (PIP) |
| :--- | :--- | :--- | :--- | :--- |
| **تحليل البروتوكول** | قراءة الترويسات والـ Cookies والـ Metadata | كائنات DTO نقية | محظور تماماً | محظور تماماً |
| **التحقق التشفيري** | فحص توقيعات JWT و RSA و mTLS ومخزن JWKS | لا يوجد | محظور تماماً | لا يوجد |
| **تجسيد كائن الهوية** | بناء وتطهير كائن `*security.Principal` | يُحقن في `context.Context` | يستهلك `*security.Principal` | لا يوجد |
| **التفويض الخشن** | نطاقات OAuth، وتطابق أسلوب HTTP، والمسارات العامة | لا يوجد | لا يوجد | لا يوجد |
| **جلب بيانات الكيان** | محظور (لا استعلامات قاعدة بيانات) | معرف الكيان بالـ DTO | استدعاء المستودع عبر واجهة | تنفيذ استعلامات SQL |
| **التفويض الدقيق** | محظور (حالة الكيان غير معروفة للنقل) | لا يوجد | فحص المالك، والمستأجر، ومحرك PDP | أمان مستوى السطر (RLS) |
| **تحويل الأخطاء** | صياغة RFC 7807 أو رموز gRPC Status | قيم أخطاء عامة | أخطاء Sentinel للمجال | أخطاء التخزين والاتصال |

## 3. خط أنابيب الدفاع في العمق (Defense-in-Depth Pipeline)

```text
طلب شبكي قادم (HTTP / gRPC)
       │
       ▼
┌─────────────────────────────────────────────────────────┐
│ 1. وسيط المصادقة النقلية (Transport AuthN Middleware)   │
│    - قراءة ترويسة Authorization                         │
│    - التحقق التشفيري الرياضي من توقيع الرمز             │
│    - الفشل السريع بإرجاع 401 Unauthorized إن كان فاسداً │
│    - حقن كائن الهوية المطهر *Principal في context.Context│
└──────────────────────────┬──────────────────────────────┘
                           │
                           ▼
┌─────────────────────────────────────────────────────────┐
│ 2. وسيط التفويض الخشن (Transport Coarse AuthZ Middleware)│
│    - قراءة النطاق المطلوب للمسار (Scope)               │
│    - مقارنته مع نطاقات الرمز principal.Scopes          │
│    - الفشل السريع بإرجاع 403 Forbidden إن كان غير كافٍ │
└──────────────────────────┬──────────────────────────────┘
                           │
                           ▼
┌─────────────────────────────────────────────────────────┐
│ 3. معالج ومهايئ البروتوكول (Transport Adapter)          │
│    - فك ترميز الحمولة إلى أمر DTO نقي خاص بالمجال      │
│    - استدعاء UseCase.Execute(ctx, cmd)                  │
└──────────────────────────┬──────────────────────────────┘
                           │
                           ▼
┌─────────────────────────────────────────────────────────┐
│ 4. حالة استخدام التطبيق (Application Use Case Core)     │
│    - استخراج كائن الهوية *Principal من السياق           │
│    - استدعاء المستودع (PIP) لجلب الكيان مقيداً بالمستأجر│
│    - تقييم القواعد الدقيقة عبر محرك السياسات (PDP)     │
│    - التأكد من تطابق المستأجر وحالة العمل               │
│    - إذا رُفض: إرجاع ErrPermissionDenied                │
│    - إذا قُبل: تنفيذ العملية وتعديل حالة الكيان وتحديثه │
└─────────────────────────────────────────────────────────┘
```

## 4. عزل المستأجرين ومنع ثغرات BOLA/IDOR

تحدث ثغرة تجاوز الصلاحيات على مستوى الكائن (Broken Object-Level Authorization - BOLA/IDOR) عندما يتمكن المهاجم من التلاعب بمعرف المورد (مثل `GET /invoices/1054`) للوصول لبيانات منظمة أو شركة أخرى.

### لماذا تعجز طبقة النقل عن حماية النظام من BOLA بمفردها؟

عند حدود طبقة النقل، لا يملك الوسيط سوى معلومتين:

1. هوية المتصل الموثق: `Tenant A`, `User 42`.
2. المعامل المستلم في الرابط: `invoice_id = 1054`.

لا يمكن لطبقة النقل معرفة مَن يملك الفاتورة `1054` دون إجراء استعلام على قاعدة البيانات. وإذا تم تنفيذ هذا الاستعلام داخل وسيط النقل:

- سيتضاعف العبء على قاعدة البيانات (استعلام بالوسيط، واستعلام ثانٍ داخل المعالج).
- تصبح طبقة النقل مرتبطة بمستودعات البيانات، مما يكسر المعمارية النظيفة.

### الحل الهندسي المعتمد والمتكامل

1. **استخراج `TenantID` أثناء المصادقة**:
   يتم استخراج معرف المستأجر حصرياً من ادعاءات التوكن الموثق، ويُحظر تماماً الوثوق بأي قيمة قادمة من روابط الـ URL أو ترويسات العميل.
2. **التمرير الآمن عبر السياق**:
   يصبح معرف المستأجر متاحاً ومحمياً داخل `principal.TenantID`.
3. **الفرض الإلزامي في طبقة التخزين (Repository Scoping)**:
   يجب أن تتضمن كافة استعلامات القراءة والتعديل قيد المستأجر كشرط إلزامي:

   ```go
   // تطبيق حصين ضد ثغرات BOLA
   func (r *invoiceRepo) GetByID(ctx context.Context, tenantID, id string) (*Invoice, error) {
       query := `SELECT id, tenant_id, owner_id, amount, status FROM invoices WHERE id = $1 AND tenant_id = $2`
       // ...
   }
   ```

4. **تفعيل أمان مستوى السطر (PostgreSQL Row-Level Security)**:
   في الأنظمة الحرجة، يتم تعيين معرف المستأجر مباشرة على جلسة الاتصال بقاعدة البيانات:

   ```sql
   SET LOCAL app.current_tenant = 'tenant_123';
   ```

   مع سياسة RLS صارمة في PostgreSQL تمنع محرك قاعدة البيانات نفسه من إعادة أي سطر لا يطابق مستأجر الجلسة:

   ```sql
   CREATE POLICY tenant_isolation_policy ON invoices
       FOR ALL
       USING (tenant_id = current_setting('app.current_tenant', true));
   ```

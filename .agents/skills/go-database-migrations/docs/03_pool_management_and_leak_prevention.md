# إدارة مجمّع الاتصالات ومنع التسريب (Pool Management & Leak Prevention)

تستخدم خدمات Go مجمّع اتصالات (مثل `pgxpool.Pool`) لإعادة استخدام اتصالات TCP مع PostgreSQL بكفاءة عالية. ومع ذلك، فإن أي خطأ في التعامل مع الـ `Rows` يؤدي إلى تسريب الاتصال وخروج الخادم عن الخدمة.

---

## 1. التشريح الدقيق لتسريب الاتصالات (Connection Leaks)

عند استدعاء:

```go
rows, err := pool.Query(ctx, "SELECT ...")
```

يتم سحب اتصال فعلي من مجمّع الاتصالات وربطه بكائن `rows`.

- **الخطأ الشائع**: قراءة بعض الصفوف ثم الخروج بدالة `return` دون استدعاء `rows.Close()`.
- **النتيجة**: لا يتم إرجاع الاتصال إلى المجمّع أبداً! بعد تكرار هذه العملية عدة مرات، يستنفد السيرفر حده الأقصى (`MaxConns`) ويعلق التطبيق بالكامل.

### القاعدة الصارمة

```go
rows, err := pool.Query(ctx, query, args...)
if err != nil {
    return err
}
defer rows.Close() // حتمي وفوري بعد التحقق من الخطأ

for rows.Next() {
    // Scan logic
}
// فحص أخطاء الاتصال أثناء القراءة
if err := rows.Err(); err != nil {
    return fmt.Errorf("row iteration error: %w", err)
}
```

---

## 2. ضبط حدود مجمّع الاتصالات (Pool Sizing)

- **`MaxConns`**: الحد الأقصى للاتصالات المتزامنة. لا تجعله كبيراً بلا مبرر (مثل 500) لأن كل اتصال في PostgreSQL يستهلك ذاكرة ويعاني من المنافسة على المعالج. المعادلة الموصى بها غالباً:
  $$\text{MaxConns} \approx (\text{CPU Cores} \times 2) + \text{Disk Spindle Count}$$
- **`MinConns`**: عدد الاتصالات الدافئة الجاهزة للخدمة دون انتظار مصافحة TCP جديدة.
- **`MaxConnIdleTime`**: إغلاق الاتصالات الخاملة بعد فترة معينة لتوفير موارد الخادم.

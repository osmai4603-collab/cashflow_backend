# معايير تصميم واجهات برمجة تطبيقات REST ومعالجة الأخطاء في Go

تحدد هذه المهارة المعايير الإنتاجية الصارمة لتصميم واجهات برمجة تطبيقات HTTP (RESTful APIs) في خدمات Go. وتضمن الواجهات اتساقاً وتنبؤية وقابلية للفهم الذاتي عبر جميع وحدات النطاق، من خلال تطبيق مغلفات الاستجابة القياسية، وتفاصيل مشاكل RFC 7807 للأخطاء، والترقيم والتصفية الآمنين، ومفاتيح عدم التكرار (Idempotency Keys) للعمليات المالية الحساسة.

---

## المبادئ الإنتاجية لتصميم الواجهات (Production API Principles)

1. **مغلف استجابة موحد (Unified Response Envelope)**:
   تتبع جميع استجابات HTTP JSON الناجحة عقداً هيكلياً متسقاً:
   - حمولات الموارد والبيانات تُغلف داخل حقل `"data"`.
   - البيانات الوصفية (الترقيم، الأعداد الإجمالية، وقت التنفيذ) تُغلف داخل حقل `"meta"`.
2. **تفاصيل المشكلات RFC 7807 لأخطاء HTTP (Problem Details)**:
   لا تُعد أبداً نصوصاً عشوائية مثل `{"error": "bad request"}`. بل أعد دائماً كائنات مشكلات مهيكلة برمجياً بنوع محتوى (`application/problem+json`) تتضمن `type`، `title`، `status`، `detail`، `instance`، والرمز الخاص بالنطاق `code`.
3. **ترقيم صفحات آمن ومقيد (Safe & Bounded Pagination)**:
   لا تسمح أبداً بعمليات مسح غير مقيدة لقواعد البيانات. وفّر حدوداً افتراضية (مثل 20 سجلاً) وافرض حداً أقصى صارماً (مثل 100 سجل). ادعم كلاً من الترقيم القائم على الإزاحة (Offset/Limit) والترقيم القائم على المؤشر (Cursor-based).
4. **عدم التكرار الحسابي للعمليات المعدلة (Idempotency)**:
   يجب على عمليات إنشاء المدفوعات، وإصدار الفواتير، والتحويلات المالية فرض ترويسة `Idempotency-Key`. إذا حدثت إعادة محاولة عبر الشبكة بنفس المفتاح تماماً، يعيد الخادم النتيجة الأصلية المخزنة مؤقتاً دون إعادة تنفيذ العملية المالية.
5. **فصل مطابقة رموز حالة HTTP (Decoupled HTTP Status Mapping)**:
   قواعد أعمال النطاق لا تعرف شيئاً عن رموز HTTP. تتولى طبقة محول الواجهة (API Adapter) مطابقة أخطاء النطاق الصريحة (`ErrNotFound` -> 404، `ErrInvalidState` -> 422، `ErrUnauthorized` -> 401).

## المعمارية: عقد الواجهة البرمجية (The API Contract)

```text
┌──────────────────────────────────────────────────────────────────────────┐
│                             الطلب الوارد (Incoming Request)              │
│       HTTP Method + Path + Idempotency-Key Header + JSON Payload         │
└────────────────────────────────────┬─────────────────────────────────────┘
                                     ▼
┌──────────────────────────────────────────────────────────────────────────┐
│                   برمجيات محول الواجهة الوسيطة (API Middlewares)         │
│   كاش عدم التكرار ─── التحقق من صحة الطلب ─── محلل ترقيم الصفحات         │
└────────────────────────────────────┬─────────────────────────────────────┘
                                     ▼
┌──────────────────────────────────────────────────────────────────────────┐
│                   مستوى تنفيذ النطاق وحالات الاستخدام                    │
│                  ينفذ قواعد الأعمال الأساسية بنقاء تام                    │
└────────────────────────────────────┬─────────────────────────────────────┘
                                     ▼
┌──────────────────────────────────────────────────────────────────────────┐
│                         منسق الاستجابات القياسي                          │
├────────────────────────────────────┬─────────────────────────────────────┤
│   النجاح: 200 / 201 Created        │   الفشل: 4xx / 5xx                  │
│   {                                │   Content-Type: application/problem │
│     "data": { ... },               │   {                                 │
│     "meta": { "total": 100 }       │     "type": "urn:problem:not_found",│
│   }                                │     "title": "Invoice Not Found",   │
│                                    │     "status": 404,                  │
│                                    │     "detail": "Invoice 123 absent"  │
│                                    │   }                                 │
└────────────────────────────────────┴─────────────────────────────────────┘
```

## الأنماط المضادة الواجب تجنبها (Anti-Patterns to Avoid)

| النمط المضاد | سبب فشله في البيئات الإنتاجية | النهج الهندسي الصحيح |
| :--- | :--- | :--- |
| استعلامات غير مقيدة `SELECT *` | استعلامات ضخمة تستنزف الذاكرة والمعالج | فرض `limit` و `offset` بصرامة مع وضع سقف أعلى (مثل 100) |
| استجابات أخطاء بنصوص بسيطة | تعذر تحليل تفاصيل الأخطاء برمجياً في الواجهات الأمامية و SDKs | إرجاع JSON مطابق لـ RFC 7807 مع حقلي `code` و `detail` مهيكلين |
| إرجاع 200 OK للأخطاء | تعطيل المراقبة وموزعات الأحمال والتخزين المؤقت | إرجاع رموز حالة HTTP الملائمة (404, 422, 401, 500) |
| غياب مفتاح عدم التكرار في المدفوعات | إعادة المحاولة الشبكية تؤدي لخصم المبلغ من العميل مرتين | فرض ترويسة `Idempotency-Key` وتخزين النتائج المكتملة مؤقتاً |
| تسريب أسماء أعمدة قاعدة البيانات | ربط عملاء الواجهة البرمجية مباشرة بمخطط قاعدة البيانات الداخلي | استخدام كائنات DTO صريحة مع مفاتيح واضحة بصيغة camelCase أو snake_case |

## قائمة التحقق لضمان جودة الواجهة (API Verification Checklist)

```text
[ ] جميع استجابات النجاح تعيد مغلف JSON قياسي بصيغة { "data": ..., "meta": ... }
[ ] جميع استجابات الأخطاء تستخدم معيار RFC 7807 (application/problem+json) مع type و title و status و code
[ ] معايير ترقيم الصفحات تمتلك قيماً افتراضية منطقية (20) وسقفاً أعلى صارماً (100)
[ ] العمليات المالية المعدلة تتطلب وتفرض ترويسة Idempotency-Key
[ ] معالجات HTTP لا تحتوي على منطق أعمال أو استعلامات SQL مباشرة
[ ] جميع حقول التاريخ والوقت تسلسل وفق تنسيق ISO 8601 / RFC 3339
```
